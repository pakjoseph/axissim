# Run provenance sidecar

`axissim run ... --json result.json` writes the established numerical result
JSON unchanged and a sibling `result.json.provenance.json` record. The
provenance schema is `axissim.run-provenance.v2`. It is generated by the C++
CLI from the same typed `Config` produced by `load_config_with_sources()` and
does not affect model execution or numerical outputs.

The sidecar records:

- Source revision and source-tree state (including untracked paths) embedded at
  CMake configure time.
- Compiler ID/version, C++ standard, build type, target platform, Qt version,
  package kind, and package identity.
- SHA-256 of the actual running CLI executable.
- The root manifest and every transitive `include` file, hashed from the exact
  bytes captured by the configuration parser.
- Referenced workload profile, mapping plan, mapping accuracy evidence, arrival
  trace, and its provenance source hashes when applicable. For provenance-
  enabled runs, each external file is read once and parsed into the resolved run
  inputs; those same parsed values are passed to the simulator. The sidecar
  hashes the exact captured bytes (`input_verification.status` is
  `exact_bytes_captured_and_used`). Later filesystem changes cannot alter the
  run or its input identity. The v2 `required_runtime_inputs` list must match
  the runtime-role records in `configuration_files`; the complete-identity
  check also matches trace, trace-provenance, profile, and mapping-plan paths
  against the resolved configuration.
- The exact result-JSON byte hash. The GUI and Python verifier compare the
  result bytes against this hash before treating the JSON/sidecar pair as
  intact.
- The explicit `--set` overrides, authored merged values, and the full typed
  resolved `Config`.
- `identity_sha256`, calculated from deterministic JSON containing both the
  identity status and provenance payload, with sorted object keys and no
  timestamp or absolute host path.

Paths in the record are logical paths relative to the root manifest. Files
outside that tree use an `external/<basename>` label and are distinguished by
their content hash. This avoids exposing or binding the result to a developer's
checkout or temporary directory.

`identity_status` is either `complete` or `incomplete`. Unknown source,
compiler, executable, or input identity is represented as `unknown` (with a
field status where relevant) and forces `incomplete`. A result can still be a
valid simulation when its provenance is incomplete; it must not be described
as a verified reproducible identity. The sidecar is evidence about inputs and
build identity, not a measured hardware record or a model-validation claim.
The GUI and Python verifier check the fields behind a `complete` claim,
including source revision/tree state, compiler, executable hash, root and
transitive input hashes, resolved configuration, result hash, and schema-specific
input-capture status. Recomputing the sidecar's own identity hash does not by
itself make an incomplete identity complete. `identity_sha256` is an unkeyed
integrity digest, not a digital signature or proof of origin; a party able to
rewrite a sidecar can recompute it. Treat `complete` as a structurally
consistent record of the evidence emitted by the simulator, not as an
authenticated attestation.

The result JSON schema (including historical schema 1.2 outputs) is not
modified. GUI result export writes both the JSON and the adjacent provenance
sidecar.

## Package provenance

`package-provenance.json` uses schema `axissim.package-provenance.v1` and is
generated during CMake configuration, not by inspecting `.git` at runtime.
Untagged builds say `artifact_kind: validation` and use a commit-derived
`package_id`; unavailable revision information remains `unknown`. A
release-labeled package requires `AXISSIM_RELEASE_TAG` to name an existing Git
tag that resolves to the exact packaged HEAD, and requires a clean source tree
with no untracked paths. This validation does
not create a Git tag, publish a GitHub Release, sign a binary, or notarize an
application.
